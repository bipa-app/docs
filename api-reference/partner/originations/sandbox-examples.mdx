<Warning>
These controls require the sandbox simulation rollout. They are not available in production. Until the backend and configuration rollout is complete, the fixture/event routes return `404`; an ordinary deployment rejects the `sandbox` field. Do not treat these examples as proof of a completed deployment.
</Warning>

Use `https://api-sandbox.agentispay.co/migrations`. Each block is **one copyable command**: replace only `REPLACE_WITH_YOUR_SANDBOX_API_KEY`. It runs Bash and requires `curl` and `jq`.

The first request obtains a fresh synthetic identity and signed document URLs. The complete import JSON is visible below, printed before submission and saved to a local `.request.json` file. It contains no real documents. Each run starts a new test; replay the saved JSON to retry the same import.

Quantities are integer strings in base units: BTC 8 decimals, USDT/USDC/XRP 6, ETH 18 and SOL 9. Send only `asset` and `quantity` in balances. Omit `network`, `contract` and `decimal_scale`.

## Advance a migration

Replace the key and returned migration UUID. This example approves a pending **simulated** review:

```sh
curl --silent --show-error --fail-with-body --include \
  'https://api-sandbox.agentispay.co/migrations/MIGRATION_ID/sandbox-events' \
  --header 'X-API-Key: REPLACE_WITH_YOUR_SANDBOX_API_KEY' \
  --header 'Content-Type: application/json' \
  --data '{"idempotency_key":"review-1","event":"approve_review"}'
```

Use these complete JSON bodies for the relevant action:

| Current stage | Event JSON | What to expect |
|---|---|---|
| `awaiting_onboarding` or `document_recapture_required` | `{"idempotency_key":"kyc-1","event":"complete_customer_kyc"}` | Normal KYC progresses toward settlement; insufficient liquidity can pause it. |
| `awaiting_activation` | `{"idempotency_key":"activation-1","event":"activate_customer"}` | Activation checks run, then settlement or a review/denial. |
| `manual_review` in example 4 | `{"idempotency_key":"review-1","event":"approve_review"}` | Import resumes toward funding and activation. |
| Pending simulated review | `{"idempotency_key":"review-1","event":"reject_review"}` | `state: denied`, `stage: terminal`, `action_required: denied`. |
| Any nonterminal stage | `{"idempotency_key":"expiry-1","event":"expire_migration"}` | `state: expired`, `stage: terminal`, `action_required: expired`; reserved assets are returned. |

For an approved activation review, send `activate_customer` again with a **new** key such as `activation-after-review`. This represents the customer resuming after Bipa reviewed the evidence.

Events return `202` while pending and `200` when completed. Replay the identical event to check its completion. Reusing a key with different content returns `409 idempotency_key_reused`; an event in the wrong stage returns `409 simulation_event_not_ready`. Only the owner can access the migration and its events. `approve_review` and `reject_review` apply only to the dedicated simulated review scenarios.

## Funding and polling

If any example reaches `awaiting_funding`, fund the missing base-unit amounts. For the two-asset examples:

```json
{
  "idempotency_key": "funding-1",
  "event": "fund_originator",
  "balances": [
    { "asset": "BTC", "quantity": "1000000" },
    { "asset": "USDT", "quantity": "1000000" }
  ]
}
```

For example 2, use its complete six-asset `balances` array. This event credits sandbox test liquidity; it does not represent a real deposit. To reliably test `awaiting_funding`, Bipa must prepare an underfunded test account. A previously funded account may proceed directly to activation or settlement.

```sh
curl --silent --show-error --fail-with-body \
  'https://api-sandbox.agentispay.co/migrations/MIGRATION_ID' \
  --header 'X-API-Key: REPLACE_WITH_YOUR_SANDBOX_API_KEY'
```

Poll every 5–15 seconds. Observe `state`, `stage` and `action_required` together. `approved` means import approval; only `settled` means migration completion. Terminal results all have `stage: terminal`, with `state` and `action_required` identifying `settled`, `denied` or `expired`.

For a stable `validating` test, use `scenario=provider_unavailable` with example 2. Send `{"idempotency_key":"provider-1","event":"recover_provider"}` before retries are exhausted to continue.

## Retry and conflict behavior

Replay the saved import JSON with the same key: expect `200` and the original `migration_id`. Change only `external_id` while the migration remains active: expect `409 migration_already_active` with that same ID for your account. Change the body while keeping the original `external_id`: expect `409 external_id_reused`.

Document recapture and manual review remain on the same migration. Continue polling; the partner does not need to import the person again. Bipa must provide the working customer handoff for real recapture; the sandbox event simulates that customer action.
